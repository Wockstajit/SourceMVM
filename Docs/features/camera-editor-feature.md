# Camera Editor Mode

The dedicated in-demo **camera editor workspace**: a Panorama overlay that frames the live game as a preview viewport with a right-side property inspector, a bottom TIMELINE dock, and workspace tools (Customize, Render). Toggle it with `mirv_filmmaker editor toggle` (commonly bound, e.g. `bind "F9" "mirv_filmmaker editor toggle"`).

Related docs: [panorama_ui_guide.md](../panorama/panorama_ui_guide.md) (how the Panorama bridge and JS architecture work), [customize-feature.md](customize-feature.md) (the Customize modal), [follow-camera/](../follow-camera/README.md) (the Follow system that the editor's Follow inspector edits), and [filmmaker_config_panel.md](filmmaker_config_panel.md) (the standalone Config panel, the editor's "little sibling").

## What the workspace is

`CameraEditorHud` is a **presentation shell** over the existing camera back-ends. It adds no new editing logic. While enabled, it:

- frames the live game as a **preview** (top-left) with a dimmed letterbox. The preview is either a crop of the full-screen frame or, with `editor scale on`, a true scaled viewport. The scaled viewport shrinks the whole frame through a D3D blit and a matching HUD CSS transform. The two scaling paths must match 1:1.
- shows a right-side **inspector** with per-mode sections (camera path / Follow camera / playback);
- docks a **bottom panel** with two tabs (`dock native|timeline`): REGULAR TIMELINE (CS2's own demo bar) or the [TIMELINE dock](#the-timeline-dock), which edits camera and scene keys together;
- suspends mirv free-cam mouse-look and shows the OS cursor while its UI wants the mouse.

Reusable workspace choices persist in `%APPDATA%\HLAE\filmmaker_settings.json`: scaled preview, bottom-panel mode, game-HUD mode, debug overlay, Path/Follow inspector tab, and the Advanced Tracking disclosure. Closing or reopening the editor does not reset them.

Path, Follow and Scene Keys use a grouped rail with one selected inspector pane. Path's selected camera and path controls share a card. Follow's mode and target controls share a card, while its Live/Stop control stays pinned above the rail. Switching panes preserves each control's state. The [shared workspace contract](../panorama/panorama_ui_guide.md#shared-workspace-contract) owns chrome, scroll and value-drag behavior.

Shot-specific state stays out of this global store. Camera transforms, selected path keys, Follow/Attach targets, offsets, rotations, FOV, and tracking values remain owned by their camera systems. One camera's setup is never copied onto another.

## Console surface

Everything routes through `mirv_filmmaker` (dispatcher: `FilmmakerCommand.cpp`; one `*Command.cpp` file per feature):

```
mirv_filmmaker editor [on|off|toggle]      the workspace itself
mirv_filmmaker editor scale [...]          true scaled preview viewport
mirv_filmmaker dock [native|timeline|toggle]   bottom dock: CS2's bar or the TIMELINE dock
mirv_filmmaker editor hud [hidden|game|full|cycle]   game UI behind the editor
mirv_filmmaker editor debug [...]          viewport/HUD debug overlay
mirv_filmmaker camtl ...                   camera timeline (scrub, keys, easing)
mirv_filmmaker marker ...                  marker/dolly path
mirv_filmmaker follow ...                  follow / lock-on camera
mirv_filmmaker grapheditor ...             TIMELINE dock: camera channels, playhead, `key <shortcut>`
mirv_filmmaker scenekeys graph ...         TIMELINE dock: scene properties
mirv_filmmaker cosmetics ...               customize backend
```

Drive the UI from netcon with short calls into predefined JS helpers (`$.Filmmaker.*`). `ui_eval` truncates at 256 bytes.

## The TIMELINE dock

One After Effects-style timeline for everything keyed in a shot. It replaced the separate CAMERA timeline tab, the camera GRAPH and the SCENE GRAPH, so camera keys and scene keys are edited side by side. The dock is 440px under the shared 36px ribbon (REGULAR TIMELINE / TIMELINE, with "N layers · N keys" on the right), and spans the screen left of the inspector.

**Layout** (top to bottom): a 72px toolbar (timecode and tick; KEYFRAMES / GRAPH; what is selected; prev key / play / next key, Cache (`scrub cache on|off`: keep the frames you play so scrubbing back over them is instant) and the speed scrubber over the interpolation strip, SNAP, Undo, Redo and Delete), the LAYERS / VALUE / KEY column header beside the overview navigator and the ruler, 22px rows that scroll, and a footer with the render range, the visible span, FIT, zoom and a scrollbar. **FIT** frames the selected keys (clicked or boxed), else the selected layer or row, else every key; pressed again while the view still frames that, it fits every key. **Go to a key**: double-click it (any row, either view, a collapsed layer's marks too), or right-click it and pick **Go to this key**.

**Layers.** The camera path is one layer: Transform > Position, Rotation, Field of view, and Path > Camera shake. Camera shake shows the shake running under the playhead. Once any key carries one, the row twirls open to Intensity (1-10) and Speed (10-100), which are keyframes: a mark on each shake key. Their values are drawn in GRAPH, not in the rows: select Camera shake (or the Path group) and switch to GRAPH for both curves, each on its own 0-to-max scale, and drag a key there to set it. **Shake runs** (`CamPathShake_EvalSnapshot`): a shake key and the next shake key with the same style are one run across any camera keys between them, and intensity and speed glide from one to the other along an eased ramp (smoothstep, `CamPathShakeRampMath.h`), so a shot can start slow and gentle and build up without a jolt. The shake runs on its own clock, the integral of its speed, so a speed ramp bends the oscillation's rate instead of making it race. Any other key runs until the next shake key of the track, or to the path's last camera key: camera keys without a shake play no part, so adding camera keys never shortens a shake (2026-10-17). **Stop the shake here** puts a Stop key that ends it. A one-shot never chains. Wherever a run ends or the style changes, the outgoing shake fades over 0.35 s. The Camera shake row's bar shows how far each run goes. Scrub or type Intensity / Speed to set them: on a camera key that carries no shake yet, that keys it with the shake running there (`pathshake set @<tick>`); elsewhere it sets the key whose run covers the playhead. A camera object's OBJECTS layer carries the same Camera shake row, on its own track with keys on any tick, which shakes the view while that camera is looked through ([filmmaker_camera_path_shake.md](filmmaker_camera_path_shake.md)). ◇ on those rows adds a shake key continuing the run (or removes one). `mvm_debug` logs `pathshake.ramp` (key, run start, ramped intensity and speed, clock) next to `pathshake.view`. Every CONFIG card with armed or keyed scene properties is another layer ("EFFECTS · LIGHTING", "ENVIRONMENT · FOG"). A layer row carries a colour swatch, its key count and an on/off switch. The camera switch is the dock's drive flag: on, a camera key edit shows the edited path, and a scrub through the path flies it while **AUTO** is on; off, the free cam stays yours. With AUTO off, dragging the playhead (or scene keys, which carry it) through the path's range leaves the view where it is (2026-10-17). **Space and the play button play the demo**: they no longer jump into the camera path (user request 2026-10-17). The camera path layer's **AUTO** button (off by default, saved as `editor.timeline.autopath`, `camtl autopath`) makes the view follow the path while the timeline plays through its keys: range-gated playback that hands the view back before the first key, and at the last key gives it to CS2's camera while the demo plays on (`CameraPath::RunAutoPath`). **J** plays the path either way. A scene layer's switch disables it (`scenekeys mute`): keys kept, nothing applied. The bar from a layer's first key to its last slides every key of the layer. Collapsed layers and groups show summary marks.

**Properties.** The value column shows the value at the playhead (X / Y / Z in their channel colours). Drag a number to scrub it at a fixed speed set when the drag starts (`scrubStep`: 1 unit a pixel for positions, 0.25° for angles, 0.1 for field of view, a 600th of the coded range at most 1 for other scene settings; Shift is 5x finer), click it to type (Enter or a click away commits). A typed camera value keys the camera at the snapped playhead; the first key at a tick keys every camera channel there, like "+ Add". A colour opens the shared CONFIG colour wheel in a tray beside the list. `◀ ◇ ▶` steps between the row's keys and adds or removes the key under the playhead. Right-click a property for Separate / Join Dimensions (Position and Rotation), Show in Graph, Add or Re-key at playhead, and for scene properties Disable and Delete.

**Keys.** A glyph's two halves say how the curve meets the key on each side: half diamond = linear, notched half = Bezier (Easy Ease, or a handle edited in GRAPH), half disc = Auto Bezier (Smooth), half square = hold (stepped properties, and the sides of a Hold key). The kind is stored on the handle (`autoTan`, saved as kind 2 in a campath `curve` and as `"auto"` in scene keys), never guessed from its slope: a flat Smooth key and an Easy Ease are the same numbers. Auto Bezier handles follow their neighbours, re-solved after every edit (`GraphExpModel::RefreshAutoTangents`, scene `RefreshAutoTangents`), so moving a key reshapes the Smooth keys around it. Dragging a handle in GRAPH, or an ease, turns that side into a plain Bezier that later edits leave alone. Ease In is the incoming (left) side and Ease Out the outgoing one, for camera and scene keys alike. Click selects (Shift adds), drag moves the selection (the lead key snaps; the edit opens only once the drag starts), drag empty track to box-select. Clicking a layer's name selects every key in the layer, so Delete then removes everything in it (`pickRow`). Clicking a scene key moves the playhead to it, and a dragged scene key carries the playhead. Right-click a key for Delete, Align, Keyframe Assistant (Easy Ease F9, In Shift+F9, Out Ctrl+Shift+F9, Smooth, Linear, and for scene keys Hold) and, on camera keys, Camera Shake. **Hold** (also on the ease strip) makes the segment leaving each selected scene key a step; Linear, Smooth or an ease on that side, or dragging its handle, makes it a curve again. Placed scene objects (lights, meshes, camera objects) that are animated show as **OBJECTS** layers with Position, Rotation and Field of view rows, and their keys hold by default ([scene-object-rigs.md](scene-object-rigs.md)). Camera Shake › lists the Rockstar Editor shakes (the rest under More shakes ›), the key's own ticked. Click one to put it on the key; each has its own › with Stronger, Weaker, Faster and Slower, which put that shake on at the stepped value (`pathshake set <key> <style> <n> <p>`) and keep the menu open on it. Menus nest to any depth, and a keep-open step reopens the same submenus with the new values. Delete, Ctrl+Z / Ctrl+Shift+Z, Ctrl+A and F9 reach the dock through `grapheditor key <name>`: the dock knows which model holds the selection and which was edited last. Selecting in one model clears the other unless Shift is held.

**GRAPH** draws the curves of the selected layer, group or property (up to eight channels), each scaled to its own range across the full height, with a legend and the snap grid. Selected keys show their Bezier handles (Shift straightens). Camera curves keep the C++ key fit as a floor; scene curves fit what they draw inside their coded range. Ranges refit between gestures and never during one.

**Time.** The ruler shows m:ss.cc at the demo's tick rate and carries the render range (work area): drag its ends or middle, released as `render range custom <in> <outExclusive>`. Click or drag elsewhere on the ruler to scrub; past the track's edge the view creeps after the cursor. The overview maps the whole demo (keys, render range, playhead, view box: drag to scroll, drag an end to zoom). The JS owns the visible window after C++ suggests it once (camera and scene key span), playback pages it AE-style, and a jump to an off-screen key lands 2% inside. Time snap (`editor.graph.snap`) quantises the playhead, key placement and drags; Alt bypasses it. The KEYFRAMES / GRAPH choice persists as `editor.timeline.view`.

**Marker limits.** A marker is checked wherever it enters the path: a placement, a typed or
dragged value (`camtl setval`), a graph edit, an undo and a load (`SanitizeMarker` in
`Movie/CamMarkers.h`). Angles may spin through many turns, up to 36000 degrees (100 turns); past that
a value folds back to the same direction within one turn. Non-finite values reset, positions stay
within 1e6 units, FOV within 1 to 179, and a runaway handle drops to 0. A saved yaw of 4.7e10 once
froze the game on every load of its demo, because every angle wrap walked 360 at a time; wraps are
one step now (`std::remainder`), and `angle-wrap-loop-tests.mjs` keeps the loops out.

Two models stay authoritative in C++: camera channels in `GraphExpModel` (`grapheditor ...`, baked into the camera path) and scene properties in the scene track (`scenekeys graph ...`). `GraphEditorExperimentHud::BuildStateJson` publishes both: the seven camera channels, `scene` (SceneKeys_AppendTimelineState), the render range, the path's marker ticks with their shakes, the tick rate and path playback.

## Scene keys

The SCENE KEYS inspector tab picks which properties are animated. Turning one on gives it a row on its CONFIG card's layer in the TIMELINE dock, where its keys and curves are edited. CONFIG stays the baseline for every property that is off, and for every tick outside a keyed span.

A property switched on has to show. The `env.*` channels (sun, fog, clouds, grading and the rest of the ENVIRONMENT family) only render while the Environment scene is on, so any `scenekeys` command that leaves one of them on also runs `environment on` when the Environment is off. A TIME OF DAY look keyed with the Environment off used to change nothing on screen.

**Names.** A property has one name, held in the catalog's name table, and both the inspector row and the timeline row show it. The name is the label of the CONFIG control that edits the same value. Where CONFIG's label only makes sense on its own page, the name adds the page's subject: CONFIG's LIGHTING > Sun "Rotate" is "Sun rotate", and its SKY > Sun & sky "Azimuth" is "Sun azimuth". Values that CONFIG keeps off its panels are named for what they drive, such as "Custom sun azimuth" for the absolute sun position. Layers follow CONFIG's tabs and cards: Effects (Lighting, Weather & Sky, Atmosphere) and Environment (Looks, Sky, Lighting, Fog, Weather, Ground), in CONFIG's order. They read "EFFECTS · LIGHTING" and "ENVIRONMENT · LIGHTING", because both tabs have a Lighting card. The inspector lists the properties CONFIG shows by default, and the rest sit under More settings.

**The playhead.** The dock drives the playhead with `grapheditor playhead`, so a ruler drag moves the demo world as well (see [live demo scrubbing](filmmaker_demo_scrubbing.md)). After any release, the playhead holds the released tick while the demo travels there, and then while the demo stays where it landed. A seek can land one tick past its target, and without the hold a key you jumped to read as "not here". A value edit at the playhead re-keys the key under it and only adds a key on a tick that has none.

**Editing.** A scene key drag sends its total offset since the press, so a step refused at another key or clamped at a range bound is not lost and the key stays under the pointer. Bezier handles stay inside the property's range, because the sampled value is clamped to it anyway. Angles are drawn the way they are sampled, the short way round (or in the key's set direction) and wrapped.

**Diagnosis.** `mvm_debug` logs `scenekeys.set` (every new key, sampled re-keys, with the playhead it used), `scenekeys.move` (sampled drags) and `playhead.hold` (hold, landed, drop and why). `mirv_filmmaker scenekeys status` prints each armed or keyed property with its keys and the value resolved at the playhead.

Tests: `SceneKeyframeTrackTests` (catalog names and groups, sampling, drag offsets, serialization), `Automation/tests/scene-graph-tests.mjs`, `scene-keys-ui-tests.mjs` and `graph-timeline-nav-tests.mjs`.

## Known contracts / gotchas

- **All Panorama work runs on the game's MAIN thread** (`RunMainThreadFrame`). Calling `RunScript` from the render thread crashes V8. See CLAUDE.md's threading section.
- **Per-frame close paths must no-op when already closed.** Closing Customize must not unconditionally tear down unrelated dropdowns.
- **Release scaled HUD styles on exit.** Config/Editor temporarily write inline Panorama transforms to match the scaled preview. Teardown uses a two-phase release. First, snap `transform` to `none`, so Panorama refreshes compositor-backed panels such as `HudBottomGradient`. Then, on the next UI tick, assign `null` to the inline `transform`, `transformOrigin`, and `transition`. The second step returns ownership to CS2's native demo-controller rule, which keeps the lower gameplay HUD above its timeline. Permanently leaving `transform: none` masks that rule.
- Round-marker rescaling, native-bar `EndPlayback`/gear integration, and the settings popup are owned by the Camera Timeline/Editor Panorama fragments.
- **The docked transport row is scaled to fit, which takes two writes, not one.** Docking narrows CS2's demo bar to sit left of the inspector. Since the 2026-10-14 CS2 build its `ControlRow` reads: play, time/tick, the 5s skips, round nav, `MvmSpeedSpacer`, the speed scrubber, `ControlRowSpacer`, player stepper, next event, camera mode, and our `MvmBarButtons` group (LOOP icon, MOUSE, CAM EDITOR, CONFIG). `arrangeRow` (CameraTimelineJs) moves the scrubber between the two flexible spacers so it sits mid-bar. Only the spacers flex; every other cluster is fixed px, so a narrow dock leaves the spacers at 0 and Panorama's default `overflow: squish` crushes the clusters during layout, before any transform applies. `fitControlRow` therefore sizes the row to its fixed content plus a 44px buffer (without this the row clips its own children at the dock width), then scales it from its left edge by `dock / needed`, floored at 0.62. CS2's own `UpdateControlRowFit` collapses its labels while `ControlRowSpacer` reads 0. While docked, `dockPopups` lifts the native controller to z58 and scales CS2's player list and round menu by the same factor, so they open above the editor at matching size. Read the fit back with `mirv_filmmaker camtl eval $.Msg($.CamTimeline.dbgBar()+String.fromCharCode(10));`. `need > avail` with `k == 1` means the fit is not running.
  - The scale factor is published as `$.MirvBarFitK`, because the speed scrubber in that row is cursor-driven. `GetPositionWithinWindow()` is transform-aware and `actuallayoutwidth` is not. Without `$.MirvBarFitK`, every drag would be off by `1/k`.
- **Every scaled-preview (VP scale) break is numbered.** The render thread classifies each present (`Filmmaker/Panorama/VpScaleBreakMath.h`, tested by `VpScaleBreakMathTests`). `missed-blit`: scaling was asked for and no blit ran, so the full-size frame sits behind the panels. `stale-rect`: the blit used a rect other than the one asked for, so the world and its frame disagree. `stretched`: the backbuffer is not the window's size, so Windows stretches every frame (counted with or without a preview). Stale and stretched count only after 3 presents, because a rect move or resize settles in one or two. `mirv_filmmaker health` prints the totals, plus `BROKEN NOW` while one is open. With `mvm_debug` running, each break writes `vpscale.break #N OPEN <reasons>` with the request, backbuffer, window and last blit at that moment, and `#N recovered after <presents>` when it ends. The native HUD side reports `[vpscale] hud break #N` (the HUD size unreadable, or a bad rect) and its recovery from the camera timeline script.
- **A one-frame UI flip needs a log, not a screenshot.** `capture-game-burst.ps1` costs ~23ms a frame at 1600x1200, so it samples roughly every third frame. A single bad frame usually falls between two captures. `mirv_filmmaker camtl eval $.CamTimeline.trace(1);` emits one `[camtl.trace]` line per CHANGE of the bar's decided state (host, tab, dock width and scale, HUD view, preview rect). `mvm_debug start` captures those lines with a frame stamp. A state that exists for exactly one frame prints twice instead of hiding.
- Playback Loop controls (toggle, range highlight, draggable In/Out flags) belong only to the Regular Timeline, including its standalone and Config-docked forms. The TIMELINE dock does not duplicate them; its ruler's gold bar is the render range. Switching tabs preserves the shared loop state and saved range.
- Dragging UI must be built from `Slider` panels. HUD JS has no mouse-move event.
